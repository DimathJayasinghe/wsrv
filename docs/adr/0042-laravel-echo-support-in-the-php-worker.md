# ADR-0042: Laravel Echo support, spoken by the PHP worker, not by the daemon

- Status: **Accepted** (2026-11-27, by the project owner in chat: "yeah go ahead, accepted, and also we should ship a completed production on the first release"). Amends ADR-0028 section 4 (see "What changed since ADR-0028"). Amendment A1 records what "completed" means for the first release.
- Date: 2026-11-27
- Deciders: project owner, maintainer assistant

## Context
A Laravel developer who wants real-time features does three things today: `broadcast(new OrderShipped)` on the server, `Echo.private('orders.1').listen(...)` in the browser, and one `.env` line to pick the server. wsrv has none of that (docs/LARAVEL.md "Honest scope"): the developer writes a worker, a ticket login and calls `Wsrv\Publisher` by hand. That is the largest remaining reason a Laravel project would not try wsrv, and the roadmap (owner, 2026-11-26) puts "Laravel and Echo" after the adoption layer.

Laravel's Echo client speaks the **Pusher WebSocket protocol** (through the `pusher-js` library). Laravel's server side is a *Broadcaster*: a class with `broadcast(channels, event, payload)` and an authentication method for private and presence channels. So there are two interfaces to meet: a wire protocol in the browser, and a PHP class on the server.

What the repository already gives (verified in the code, 2026-11-27):

- The daemon accepts **any origin-form request target** on the WebSocket listener (`/app/KEY?protocol=7` passes; nothing routes on the path). With `handshake_hook=true` the worker also sees the path and the raw query (src/server/handshake_decider.hpp).
- The worker **can send a text frame from its `open` handler** (the daemon queues the 101 first), can **subscribe a connection to a room** and unsubscribe it, can send to one connection, and the daemon fans a published message out to a room without the worker (ADR-0024, ADR-0028). One worker attaches per daemon.
- A topic name is 1 to 128 bytes of `[A-Za-z0-9._:/@-]`. `private-`, `presence-`, `private-encrypted-` and `App.Models.User.1` pass. Pusher also allows `=`, `,` and `;`, and names up to 164 bytes; wsrv refuses those.
- Limits already exist and are global: 64 topics per connection, 10 000 subscribers per topic, 100 000 subscriptions, 1 024 topics, 64 KiB per published payload (all configurable). A refused subscribe comes back as `LIMIT`.
- `except` (a connection id to leave out) is a `uint64` on the wire and an `int` in PHP. This is what Laravel's `toOthers()` needs.
- The C++ code has **no HMAC, SHA-256 or MD5** (`src/crypto` has SHA-1 and Base64 only, for the handshake). PHP has `hash_hmac` and `hash_equals`.
- There is no list-members command anywhere in the IPC or the daemon (ADR-0028: "not in 1.0"). Presence state must be kept by the application.
- When the worker disconnects, its rooms are dropped at once and its connections are closed with 1012 after the grace period (IPC_PROTOCOL section 6). So worker state and connection state die together, which makes worker-held presence state coherent.

## Decision

### 1. Where the Pusher protocol is spoken: in the PHP worker (option A2)
A new part of the PHP package, `Wsrv\Pusher\Gateway`, is a worker plugin. It answers the Pusher WebSocket protocol using only commands the daemon already has. **The daemon, the IPC protocol and the C ABI do not change.**

What it does, per connection:

1. On `open`: send `pusher:connection_established` with a `socket_id` and an `activity_timeout`.
2. On a `pusher:subscribe` frame: for a **public** channel, `subscribe($channel)` and answer `pusher_internal:subscription_succeeded`. For a **private** or **presence** channel, first verify the signature (section 3), then subscribe. A bad signature, a refused name or a `LIMIT` answers a `pusher:error` and subscribes nothing.
3. On `pusher:unsubscribe`: `unsubscribe`. On `pusher:ping`: `pusher:pong`.
4. Presence channels: keep the member table (section 4) and publish `pusher_internal:member_added` and `member_removed`.
5. On `close`: drop the connection's presence entries and publish the `member_removed` events. Room subscriptions end by themselves (the daemon does it).

**Fan-out stays in C++.** A broadcast is one `publish` to a room; the worker is only on the path for connect, subscribe, presence and close, never per delivered message. This keeps the benchmark story intact (ADR-0028 and BENCHMARKS.md measure that path).

### 2. The server side: `Wsrv\Laravel\WsrvBroadcaster`
A Laravel Broadcaster (`BROADCAST_CONNECTION=wsrv`) with two jobs:

- `broadcast($channels, $event, $payload)`: for each channel, `Publisher::publish($channel, $json, except: $conn)`, where `$json` is the Pusher event envelope and `$conn` is decoded from the `socket` Laravel passes for `toOthers()` (the `socket_id`, which carries the connection id).
- `auth($request)` and `validAuthenticationResponse(...)`: run Laravel's own channel authorisation callbacks (`routes/channels.php`), then return the signed response `pusher-js` expects. Laravel's `/broadcasting/auth` route keeps working unchanged. The signature is `hash_hmac('sha256', ...)` with the app secret, in PHP.

The app key and secret are ordinary Laravel configuration shared by the Broadcaster (which signs) and the Gateway (which verifies): the Pusher model. The Gateway takes the secret from the code that builds it (read from the environment or a mode-0600 file by the application), never from a command line.

### 3. Security rules (each gets a test)
1. **Signatures** are compared with `hash_equals`. A private or presence subscribe without a valid `auth` is refused and subscribes nothing. A signature is bound to the `socket_id`, the channel and (presence) the `channel_data` string, so it cannot be replayed on another connection or channel.
2. **`socket_id` is built by the gateway** from the connection id and a random part, and sent in `connection_established`; a client never chooses it. The connection id is read back from a `socket_id` only for `except`, and a forged one can at worst leave one other connection out of one broadcast, because every signature is bound to the real `socket_id` of the subscribing connection.
3. **Every inbound frame is untrusted JSON.** The daemon's `max_message_size` already bounds it (recommended 16 KiB for a Pusher deployment; documented). The Gateway additionally decodes with a depth limit, requires `event` to be a string and `data` to be an object or a string, and answers anything else with `pusher:error` without throwing. A handler that throws would be reported by the Supervisor and not take the link down, but a gateway must not rely on that.
4. **Name policy:** a channel name that wsrv cannot carry (`=`, `,`, `;`, longer than 128 bytes) is refused with an error frame, never rewritten. A rewrite would let two Pusher names collide on one topic.
5. **Presence bounds:** `channel_data` at most 2 KiB per member (`max_channel_data_bytes`, default 2048: Pusher documents 1 KiB, and a Laravel `user_info` with a name, an avatar URL and a few flags is well past a few hundred bytes), at most 100 members per presence channel by default (configurable), and one entry per user id per channel (a second connection of the same user adds a connection, not a member).
6. **`client-*` events (whispers) are not supported in the first release.** A frame for one is answered with an error. They need rate limits and a decision about trust; a later amendment may add them, off by default.
7. **No encrypted private channels** (`private-encrypted-`): refused with an error. The server cannot read what the client encrypts, and the feature needs key handling that this ADR does not take on.
8. **The app secret is never logged** and never appears in an exception message.

### 4. Presence state: per daemon, held in the worker
A `members` table per presence channel, keyed by user id, with a reference count of connections. It lives in worker memory. Consequences, stated in the guide:

- With one worker per daemon (the only supported layout) it is exact for the connections that daemon holds.
- With several daemons (DEPLOYMENT.md section 7) each daemon sees only its own members. Presence across nodes needs a backplane, which does not exist (planned 1.x). Until then, the guide says so and recommends one daemon for presence channels.
- A worker restart closes its connections (1012 after the grace period), so no stale member list outlives the connections it described.

### 5. What does not change, and what will not work
- **The stock `pusher` and `reverb` Laravel drivers will not work** against wsrv: they call the Pusher HTTP API (`POST /apps/{id}/events`, signed with MD5 and HMAC), which wsrv does not implement. The driver is `wsrv`. Implementing the HTTP API is rejected for now (Alternatives).
- Delivery is at most once. A browser that reconnects gets no replay (IPC_PROTOCOL section 6), and `pusher-js` re-subscribes by itself.
- Origin checks, TLS, per-IP limits, the buffer budget and every other daemon control apply unchanged; the Gateway sits behind them.

### 6. Packaging, version, dependencies
- Code in `wsrv/client`: `Wsrv\Pusher\*` (framework-free: frames, signature, presence table, the Gateway) and `Wsrv\Laravel\*` (the Broadcaster, a service provider, the `wsrv:echo` Artisan command). Laravel is a `suggest`, not a `require`: a plain PHP user pays nothing.
- **No runtime dependency is added** (PHP `hash_hmac`, `json_decode`, `random_bytes`). The pure core is tested without Laravel installed. The Laravel glue is a thin layer and is tested the way the existing guide is: by hand against a real Laravel app, then in CI only if a development dependency on `illuminate/broadcasting` is approved separately (it is a download and an ADR-level dependency decision).
- **Version: 1.1.0** (decided as 1.2.0; moved to 1.1.0 on 2026-11-27 by the maintainer assistant on the advisor's advice, because 1.1.0 was still unreleased and the first release should carry the finished feature, reached through `1.1.0-rc.N` as the release rules require; a new feature in the PHP package; the daemon and the IPC protocol are unchanged, the C ABI stays 1.1).

### 7. Tests, and the gate for the word "works"
1. Unit tests for the pure core, replaying frames shaped like the ones `bench/compare/wsbench` already sends and expects against Reverb (`pusher:subscribe`, `connection_established`, `subscription_succeeded`, ping and pong), plus signature vectors, presence transitions, and a property test of random and malformed JSON asserting that no exception escapes and no bound is exceeded.
2. A test against a real `wsrvd` with a hand-written WebSocket client (the PHP package's tests already do this for the sidecar).
3. **An interoperability run with the real `pusher-js` and Laravel Echo** (npm, a few MB) is the gate before any document says "works with Laravel Echo". It needs a download, so it needs the owner's yes first (metered connection). Until it passes, the docs say "implemented to the Pusher protocol, not yet verified against `pusher-js`".

## Facts that were checked before the code, and what is still open
The first draft was written from recall. Before implementing, these were checked against sources that were on hand (Laravel Reverb's server and the `pusher-php-server` SDK, read from a local image; read only, nothing copied) and against the signature vectors Pusher publishes:

- Frame shape: `event`, `channel`, and `data` as a JSON-encoded *string* for server events; `socket_id` is `digits.digits`; `activity_timeout` is the number of seconds after which the client pings.
- Signatures: `key:` plus HMAC-SHA256 over `socket_id:channel` (presence: `socket_id:channel:channel_data`). The test suite carries the published vectors.
- Error codes and messages (4001, 4009, 4200, 4301, subscription error 4300) as Reverb sends them.
- Laravel's `Broadcaster` contract, `UsePusherChannelConventions`, the `socket` key of the payload and `BroadcastManager::extend`. Verified by running the glue against a real Laravel 13 application (`tests/laravel_check.php`).
- Encrypted channels: `shared_secret = base64(SHA-256(channel . master key))`, payloads as libsodium secretbox, as in the SDK.

The interop gate of section 7 was run on 2026-11-27: the real `pusher-js` 8.6.0 and `laravel-echo` 2.6.3, in Chrome, against a real `wsrvd` and the gateway (`tests/echo_browser/run.php`, 11 of 11 checks, including a restart of the daemon and the worker under connected browsers). It found no gateway bug, but it corrected two things I had assumed: `pusher-js` posts its auth request form-encoded, not JSON (only the test stub was wrong), and for a join followed at once by a leave it still sends `pusher:subscribe` and sends `pusher:unsubscribe` only after the success, so other members see a join and then a leave, as on Pusher itself. The same page was then run against a real Laravel 13.43 application (session, CSRF, `Broadcast::routes`, the `wsrv` driver, `php artisan wsrv:echo` reconnecting after the daemon restart) with a real `wsrvd`: 11 of 11 (`tests/echo_browser/laravel/run.sh`). Those 11 checks used small pages. After an independent review of the default limits the page was extended with one that joins 60 channels in one burst, also again after the restart; on the gateway as it was, both new checks failed with `LimitReached` (Amendment A1, item 8), and on the fixed one both runs pass 12 of 12. Not run: other browsers, the `pusher` broadcaster of Echo, Laravel 11 and 12.

## Alternatives considered
1. **The daemon speaks Pusher (option A1).** Rejected. It needs JSON parsing of wire data, HMAC-SHA256 and MD5 in C++ (`src/crypto` has neither), presence state in the event loop, new config keys, new fuzz targets and an ABI decision, all on the code that holds every socket. The only gain is that a worker is not on the subscribe path; the benchmarks do not show that path as a bottleneck. Revisit only if a measured need appears.
2. **A custom Echo connector over `clients/js` (option B).** Not chosen as the primary path: every Laravel user would change their JavaScript and depend on a connector that is not the standard `pusher-js`. It remains possible later, cheaply, as a second door onto the same Gateway.
3. **Implement the Pusher HTTP API so the stock drivers work.** Rejected for now. It needs an HTTP listener (in the daemon: more C++ and MD5/HMAC; in the worker: a second event source in a loop that must stay responsive) and request signing. A Laravel Broadcaster is a few dozen lines; the HTTP API is a protocol. Revisit if users ask to keep the `pusher` driver.
4. **Do nothing; keep the guide.** This is what ADR-0028 chose, for lack of evidence of friction.

## What changed since ADR-0028
ADR-0028 section 4 said a Broadcaster driver would be built "only if the guide shows real friction. Not built speculatively." There are not yet users to show friction. What changed is the owner's roadmap (2026-11-26): Laravel and Echo support is a goal in itself, a reason to adopt, not a reaction to complaints. This ADR therefore **amends that sentence** (an amendment note is added to ADR-0028 when this ADR is Accepted). It does not make the claim that users asked for it.

## Consequences
- + A Laravel app gets `broadcast()`, `Echo.private()`, `Echo.join()` and presence by changing `.env` and one config block, with the daemon unchanged and fan-out still in C++.
- + No new attack surface in the process that holds the sockets.
- − Presence is per daemon. Several nodes need a backplane first.
- − `client-*` whispers, encrypted channels and the Pusher HTTP API are not there in 1.1.0.
- − One more thing the PHP worker does: per-subscribe signature checks cost a little CPU in the single worker (a subscribe, not a message, so it is bounded by connect rate).
- − Until the interop run passes, the claim is "implemented to the protocol", not "works".

## Amendment A1 (2026-11-27): decisions taken while implementing

The owner accepted this ADR and asked for a completed production release first, not a reduced first cut. These points were open or left out of the first text and are now decided:

1. **Client events (whispers) are in the first release.** Echo's `.whisper()` and `listenForWhisper()` send `client-*` events. They are on by default, only for a connection that is a member of a *private or presence* channel (never public), at most `client_events_per_second` (10) per connection, only with an object or array as data, and the relayed frame is built by the server: the event name, the channel and the *signed* user id (presence) are the server's, so a browser cannot forge another member's id or add fields. They are refused on `private-encrypted-*` channels, as `pusher-js` refuses them. They can be switched off (`client_events => false`), which answers with Pusher's 4301. Leaving a channel before the daemon has answered the join cancels the join (the daemon room is left again, nobody is announced).
2. **Encrypted channels (`private-encrypted-*`) are in the first release.** The broadcaster derives the shared secret and encrypts payloads with libsodium (`ext-sodium`, in PHP since 7.2). If the master key is not configured, broadcasting to such a channel is an error: the payload is never sent in the clear to a channel the browser expects to be encrypted.
3. **One daemon.** `toOthers()` leaves a connection out by the daemon's connection number inside the socket id, and presence is held per worker. Both are only correct with one daemon, so the broadcaster takes a `Wsrv\Publisher`, not a `ClusterPublisher`. Running several daemons with the Pusher protocol is not supported in 1.1 (a shared presence store would be a later ADR).
4. **Values JSON cannot carry back out.** A browser can send a number such as `1e999`, which decodes to infinity and cannot be re-encoded. The gateway treats it as a bad frame (4200, one strike); found by the commit security review, with tests.
5. **Limits are configuration, validated at start.** Every bound (frame size, channels per connection, presence members, channel data size, the message rate and burst, the whisper rate, strikes) has a default for a public site and a range check; an unknown option name is an error.
6. **Optional strict app key.** With `check_app_key` (daemon `handshake_hook`), a URL that does not end in `/app/<key>` is refused with 404 at the handshake. Off by default because the key is public and the signature is what protects private channels.
7. **User authentication (`pusher:signin`, Echo's `user()` and watchlist) is not supported.** It is a separate Pusher feature that Laravel's `resolveAuthenticatedUser` serves; the gateway answers a `pusher:signin` frame with a 4200 error, once, without a strike. Listed as a limit in the docs, not hidden.
8. **The defaults must carry what the real client does.** `pusher-js` sends the `pusher:subscribe` of every channel of a page back to back, on load and after each reconnect, before the daemon has answered one. The first limits (at most 8 joins waiting for the daemon, 30 frames per fixed second, 8 strikes) answered a page with more than a few channels with `LimitReached`, or closed it with 1008 so that it reconnected into the same burst. An independent review of the defaults raised it; the real library reproduced it (60 channels: `LimitReached`, "Too many subscriptions in progress"). Fixed, test first: (a) no separate cap on joins in progress, because each counts against the channel quota and is bounded by it; (b) one token bucket for all frames, refilled at `messages_per_second` and as large as `message_burst`, which the configuration will not let be smaller than the channel quota plus 16 and which defaults to the quota plus 64; (c) a whisper over `client_events_per_second` is answered with 4301 and costs no strike (Reverb answers a client over its rate with the error alone and only closes it if `terminate_on_limit` is set), because the bucket on all frames is what ends a real flood; (d) the limiter clock is monotonic. The 60-channel page is now a check in both browser runs, and 64 channels in one burst is a check against a real daemon in CI.

## Amendment A2 (2026-11-27): running the gateway, not only building it

A review of the release from the side of the person who will run it found three gaps that the tests of A1 do not cover: one limit that closes honest clients over *time*, nothing to read from a running gateway, and no loop in the worker to read it from. Decided before any code:

1. **A strike is a recent violation: quiet time forgives it.** Until now the count only went up. A page open for a week that sent one malformed frame a day was closed on the eighth day, however well it behaved in between. Closing a connection is only defensible when it answers *sustained* abuse. So when a strike comes, one earlier strike is forgiven for each full 60 seconds since the previous one (or since the connection opened). A connection may break a rule once a minute for as long as it likes; faster than that the strikes pile up and at `max_strikes` it is closed. Whole strikes and whole minutes, on purpose: a first design that leaked a fraction of a strike every second was dropped when the real-daemon check "eight bad frames close the connection" failed, because eight strikes a few milliseconds apart summed to 7.9993. A burst is counted exactly and a flood is unaffected (eight strikes in half a second; a minute of quiet forgives one). The 60 seconds is a constant, not an option: the number that matters to a site is `max_strikes`, and a second knob would only lengthen the guide. Tests first: one bad frame an hour for ten hours must not close the connection; a burst closes at the eighth; one every 59 seconds closes at the eighth and one every 60 seconds never; three quiet minutes forgive three strikes and no more; a day of silence is no credit; a clock that steps back is no debt.
2. **The gateway can be read: `Gateway::stats()`.** It returns a `GatewayStats` value: gauges (connections, channels joined, joins waiting for the daemon, presence channels, presence members, the PHP memory in use) and counters since start (connections opened, frames received, joins, and the answers `4200` bad frame, `4009` unauthorized, `4301` rate limited, `4300` subscription error, joins the *daemon* refused (`daemon_refused`: its broker limits), and connections closed for strikes). Nothing in it is a string from a peer, so it cannot be used to inject a log line. `wsrv:echo` writes one line of it to stderr every `--stats-interval` seconds (default 60, `0` turns it off). Why counters and not a log line per event: a client chooses what the server logs, so a flood of bad frames would be a flood of lines (ADR-0037 gives every event a limit; here the limit is the counter). Why these: *is it leaking* (every gauge returns to zero when the browsers are gone), *is it attacked* (4009, 4200, 4301, strike closes), *does it keep up* (frames and joins per interval), *is the daemon too small for the site* (`daemon_refused`). That last question was added after the load run: with the daemon's default `broker_max_topics` of 1024, 3000 browsers that each join a private channel of their own (about 1000 users is where a site meets it) saw 3918 of 12 000 joins answered `LimitReached`, correctly and with everything cleaned up, but nothing told the operator whose limit it was; `subscription_errors` also counts a browser over its own quota. The gauges are what the churn test and the soak assert.
3. **`Worker::every(float $seconds, callable $fn)`: a periodic call inside `run()`.** The loop belongs to the worker (and to `Supervisor`, which calls `run()`), so the interval has to live there. It is checked after each `step()`, so a call is at most one poll interval late; it does not catch up after a long handler; an exception leaves `run()` like one from a handler does, with the next call already scheduled. A signal (`SIGALRM`) was rejected: it interrupts `stream_select()` and would make the link code handle `EINTR` for a log line. This is an additive method on a class the 1.x promise covers (a minor change).
4. **A message too large for the daemon fails that send, not the link.** Found while reading the code for what a running gateway can hit: `Client` refuses a message larger than the daemon's frame (the `max_frame` of its HELLO_OK, which is `ipc_max_frame`, by default `max_message_size` plus 64 KiB) by throwing `ProtocolError`, and `Supervisor` treats every `ProtocolError` as a lost link: it drops the connection to the daemon, which closes every browser, and reconnects. For a presence channel the answer to a join carries the member list, up to `max_presence_members` times `max_channel_data_bytes` (100 times 2 KiB by default; with the JSON-in-JSON escaping a worst-case list is about 513 KB, not 200 KB; an operator who raises both can pass the frame). One member whose `user_info` is large, in a channel that is nearly full, would have disconnected everyone. Decided: (a) a new `Wsrv\MessageTooLarge extends ProtocolError` (so a `catch (ProtocolError)` written for 1.0 still catches it; `ProtocolError` stops being `final`) is thrown for a send over the frame, before any byte is written, and `Supervisor` reports it like a handler's exception and keeps the link; (b) the gateway builds the `subscription_succeeded` frame *before* it announces the member, and if it cannot be sent the join fails alone: the connection leaves the room and the member table, the browser gets `pusher:subscription_error` (`ServerError`, "The member list is too large to send"), nobody else hears of a member who never joined, and the failed join is not counted as a join; (c) a repeated subscribe, which is answered again with the current list, takes the same way out if the list has grown past a frame since: the connection leaves as if it had asked to, and the others are told. What is not done: refusing to *start* when the limits can produce a list over the frame, because the frame is known only after the handshake and a smaller member count is the common case; the guide gives the formula (`members x (2.33 x max_channel_data_bytes + 1 KB)`) and flags that cover the worst case with the defaults. **Amended by ADR-0043:** the frame was not the only limit. The daemon cannot send one browser a message over `2 x max_message_size - 16` bytes and used to drop it while answering OK, so a list between that and the frame got no answer at all. The daemon now announces a frame limit capped to that size, so this item's clean failure holds for both limits; and the gateway closes (1011) a browser whose join answer the daemon refuses to queue.
5. **Not done here: superseded by amendment A3, which found this was not safe to leave.** *A list of the public channels a site really has.* Any browser may join any public channel name, and each distinct name is a room in the daemon's broker (`broker_max_topics`, global, ADR-0024 A4); one connection can make 64 of them and one address 100 connections. The bound is the defence, and `daemon_refused` is how it shows. An allowlist of public channel names or patterns (`options.public_channels`) would close it for the sites that know their names; it is an option with its own semantics (wildcards, the Laravel convention of one channel per model) and wants its own decision. *Answering a repeated subscribe.* A connection that sends `pusher:subscribe` again for a channel it is in is answered again with the current list, as Pusher does, at the price of building the list each time; the message bucket bounds it (30 a second by default), and `pusher-js` never does it. Counting it as a strike would be a rule the protocol does not have. *A start-up check that `max_presence_members * max_channel_data_bytes` fits the daemon's frame.* The frame is known only after the handshake, the product is a worst case that real `user_info` rarely approaches, and the failure is now one refused join; the guide gives the rule. *A metrics HTTP endpoint or a Prometheus text file:* the worker has no HTTP server, and a file exporter wants its own decision about paths and permissions; the line is parseable (`key=value`) and can be scraped from the journal until then. *`SIGUSR1` to print on demand:* same signal problem. *Limits per client address in the gateway:* the daemon already enforces them at accept (ADR-0021), and the gateway only sees connection numbers.

What does not change: the wire behaviour, the defaults of the limits, the message bucket, the rule that a whisper over its rate costs no strike.

## Amendment A3 (2026-11-27): anonymous public channels cannot be allowed to fill the daemon

- Status: **Accepted** (2026-11-27: the owner said "yes go ahead" to the plan that made it a release blocker). Decided by the advisor on the owner's standing instruction that design questions go to the advisor. It is a **release blocker for 1.1.0**: the first release must not ship the hole below.
- Supersedes item 5 of A2 ("the bound is the defence").

**The finding.** A security review of the A2 branch looked again at item 5 and then *measured* it instead of reasoning about it. On the default daemon and the default gateway, 16 scripted connections from one address, each joining 64 distinct public channel names (no signature is needed for a public channel), joined 1 023 names and were refused the 1 024th in 0.07 seconds, which is `broker_max_topics`. A legitimate user who logged in afterwards got `LimitReached: The server is at its channel limit` for `private-user.7` and `presence-room.1`. Joining a name somebody already held still worked, since it needs no new topic. So an unauthenticated visitor from one address could keep every *new* channel of a real site closed, with default settings, in under a second and without breaking a single rule of the per-connection or per-address limits. A2 had called this "the bound is the defence": a bound that an anonymous visitor can use up on behalf of every signed-in user is not a defence, it is the thing being attacked.

**Decision.**

1. **A budget on public names: `max_public_channels`** (`GatewayConfig::$maxPublicChannels`, default **512**, range 1 to 1 000 000). The gateway counts the *distinct public names it holds*, each name once however many connections are in it, counting a join the daemon has not answered yet (it is about to cost a room). A join to a name already held is never refused: it costs the daemon no new room. A new public name when the budget is used up is answered with `pusher:subscription_error` `LimitReached`, with **no call to the daemon and no strike** (an honest page may simply ask for a lot). The budget is checked where a join is *sent to the daemon*, and given back when the daemon refuses or cancels it, when the connection leaves the channel, and when it closes. Private and presence names are not counted: a signature decides who may make those. The default 512 is half of `broker_max_topics` (1 024), which leaves the rest of the table to private and presence rooms; the sizing table of the guide says to raise both together.
2. **An allowlist: `public_channels`** (`GatewayConfig::$publicChannels`). `null` (the default) means any public name: nothing changes for a site that does not set it. A list means only those: an exact name, or a prefix with **one trailing star** (`orders.*`); nothing else is a pattern (no star in the middle or in front, no star alone, which would be `null`). `[]` means no public channel at all, which is right for a site that only uses private and presence channels. Entries are validated when the configuration is made, with the rules of `ChannelName` (a private or presence name, a cache channel, a bad character or a name over 128 bytes is refused, so a typo does not silently allow or deny more than meant), and at most 1 000 entries are accepted. A denied join is answered `pusher:subscription_error` `AuthError`, again with no call to the daemon and no strike. The list is checked **before** the budget, so a name the site does not have never costs budget.
3. **Visible.** Three numbers are appended at the *end* of the statistics line (the order of the earlier fields does not change): `public_channels` (a gauge: the names held now), `public_denied` and `public_refused` (counters). The Laravel `options` gain `public_channels` and `max_public_channels`.
4. **What this does and does not close, said plainly.** With the budget alone, an anonymous visitor can still fill the *public* budget and so keep new *public* names closed to everybody (they cannot touch the private and presence rooms of signed-in users any more, which is the harm that was measured). Only an allowlist of exact names removes that too, because then a visitor cannot make a name the site does not have; a prefix such as `product.*` still lets a visitor make `product.1`, `product.2`... up to the budget. So: a site whose public channels are a fixed set should list them exactly; a site with open-ended public names should know that the budget is shared, and size it. A site that wants no anonymous channels sets `[]`. The default stays open (`null`) because the alternative, closed by default, would break every site that follows the Echo documentation for a public channel on the first run; the guide says in its first section that unset means open.
5. **Where it is enforced.** In the gateway, not the daemon: the daemon knows nothing of "public" (a name is a name), and putting the rule in the worker keeps ADR-0042's boundary. The daemon's own table stays the last wall, and `daemon_refused` still counts it.

**Tests (first, watched failing).** A real-daemon check on the default limits: 16 connections × 64 names, then a signed private and a presence join must succeed, a name already held must still join, and `daemon_refused` must stay 0. Unit tests for the configuration (every form accepted and every form refused), the allowlist, the budget, the reservation lifecycle (held while waiting, given back on daemon refusal, cancellation, leave, close), and the churn test now recomputes the held names from the connections' own state at every step and checks that the gauge returns to zero.

**Consequence for A2's other statements.** A2 and lesson 57 said a rising `daemon_refused` means "the daemon is too small, not a misbehaving client". That was too narrow: with the budget, a flood of public names shows as `public_refused`, and `daemon_refused` still means the daemon's own limits were reached (a real size problem, or private and presence names in numbers a single site would not make). The guide's table and the docblock say so.
